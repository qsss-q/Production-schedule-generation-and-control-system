# Итоговая техническая документация проекта

**Проект:** система формирования и контроля производственного графика коксовой батареи  
**Версия документации:** 26.11.2026  
**Основа:** конечный архив `coke_factory_api_tests_postgres.zip`, включая API-контрактные тесты и интеграционные тесты PostgreSQL.

Документ описывает фактическое состояние исходного кода. Он не приравнивает демонстрационные данные к промышленной телеметрии и не приписывает проекту функции, которые пока не реализованы.

---

## 1. Назначение и границы системы

Проект предназначен для формирования, хранения, отображения и контроля производственного графика коксовой батареи. Backend предоставляет REST API для справочников, настроек, операций, версий графика, уведомлений и аудита, а также API для взаимодействия с динамической моделью производства.

В рамках командной разработки ответственность разделена:

- **Backend/API и база данных:** REST-контроллеры, бизнес-сервисы, JPA-сущности и репозитории, PostgreSQL, обработка ошибок, Docker-конфигурация и тесты API/БД.
- **Симулятор:** отдельный модуль `simulator/`, содержащий модель батареи, печей, машин, событий и планировщиков. В рамках последней доработки API-контуров исходники симулятора не изменялись.
- **Frontend:** отдельное React-приложение, которое обращается к backend через HTTP API.

### 1.1. Что важно не смешивать

В системе существуют два разных хранилища состояния:

1. **PostgreSQL** хранит долговременные прикладные данные: справочники, операции, версии графика, настройки, уведомления, температурные измерения и журнал аудита.
2. **Симулятор** хранит текущее состояние модели в памяти backend-процесса: модельное время, состояния печей и машин, события и историю фактических выдач. Состояние можно экспортировать и импортировать JSON-файлом, но оно не является обычной записью PostgreSQL.

Поэтому перезапуск backend не должен удалять данные PostgreSQL, но без экспорта/импорта может сбросить текущее состояние симулятора.

## 3. Архитектура

```text
Браузер оператора
       |
       v
Nginx / React frontend  (localhost:5173)
       |
       | /api/** и /api/v1/**
       v
Spring Boot REST API    (localhost:8080)
       |                         |
       | Spring Data JPA         | SimulatorService
       v                         v
PostgreSQL 15              Simulator в памяти процесса
(localhost:5432)           + планировщики B1/B2/B3
```

### 3.1. Основные пакеты backend

| Пакет | Роль |
|---|---|
| `controller/` | Принимает HTTP-запросы, проверяет параметры и вызывает сервисы/репозитории |
| `service/` | Содержит прикладную логику, планирование, импорт, аудит и фасад симулятора |
| `entity/` | JPA-сущности и перечисления статусов/типов |
| `repository/` | Интерфейсы Spring Data JPA для чтения и записи в PostgreSQL |
| `dto/` | DTO и оболочка ответа `ApiResponse` для API `/api/v1` |
| `exception/` | Единый REST-обработчик исключений |
| `config/` | Конфигурация приложения, включая CORS |

Ключевые классы:

- `CokeFactoryApplication` — точка входа Spring Boot; включает планируемые задачи.
- `SimulatorService` — фасад над экземпляром симулятора, предоставляет снимки состояния и команды управления.
- `ScheduleRunService` — создание версий графика, вызов алгоритмов, сохранение операций, расчёт метрик и ручная корректировка.
- `ScheduleService` — сценарий формирования графика из API симулятора.
- `DirectoryCsvService` — импорт справочников печей и машин из CSV.
- `AuditService` — запись действий в `audit_log`.

### 3.2. Разделение API

В проекте исторически используются два пространства адресов:

- `/api/...` — преимущественно CRUD и чтение данных PostgreSQL. Ответы обычно представляют собой обычные JSON-объекты или списки.
- `/api/v1/...` — API динамического симулятора и версионирования графика. Успешный ответ обычно возвращается в оболочке `{ "success": true, "data": ..., "error": null }`.

После последней доработки `ApiExceptionHandler` применяется ко всем контроллерам. Ошибки обеих групп API возвращаются в едином формате `ApiResponse` с `success: false` и заполненным `error`. Успешные ответы legacy-маршрутов `/api/...` не переписывались в новую оболочку.

### 4.4. Формат ошибок

Глобальный обработчик `ApiExceptionHandler` формирует следующие ответы:

| Ситуация | HTTP | Код |
|---|---:|---|
| Ошибка проверки входных данных (`IllegalArgumentException`) | 400 | `VALIDATION_FAILED` |
| Нечитаемое тело запроса / некорректный JSON | 400 | `UNREADABLE_BODY` |
| Необработанное исключение | 500 | `INTERNAL_ERROR` |

Пример:

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Описание ошибки"
  }
}
```

Для HTTP 500 клиент получает нейтральное сообщение «Внутренняя ошибка сервера», а внутренние детали исключения не возвращаются.

## 5. Модель данных PostgreSQL

Сущности проекта находятся в `src/main/java/org/example/coke_factory/entity/`, репозитории — в `repository/`.

| Таблица | Сущность | Назначение |
|---|---|---|
| `equipment` | `Equipment` | Справочник оборудования, тип и доступность |
| `coke_ovens` | `CokeOvens` | Печи, номер батареи, состояние, прогресс, технологические параметры и ссылка на оборудование |
| `schedule_operations` | `ScheduleOperation` | Плановые и фактические интервалы операций, статус, приоритет, ручная отметка и отклонение |
| `schedule_runs` | `ScheduleRun` | Версии рассчитанного графика, алгоритм, seed, входной hash, метрики и связь с родительским прогоном |
| `schedule_settings` | `ScheduleSettings` | Параметры планирования и активный профиль настроек |
| `notifications` | `Notification` | Уведомления о событиях и отклонениях |
| `audit_log` | `AuditLog` | История действий оператора и системных изменений |
| `oven_temperature_readings` | `OvenTemperatureReading` | Температурные измерения по печам |

### 5.1. Основные связи

- `coke_ovens.equipment_id` ссылается на `equipment.id` (связь `ManyToOne`).
- `schedule_operations.oven_id` ссылается на `coke_ovens.id`.
- `schedule_operations.run_id` связывает операцию с прогоном из `schedule_runs`; поле хранится как строковый идентификатор.
- Температурные измерения и журнал связываются с соответствующими объектами через идентификаторы/поля, определённые в сущностях.

### 5.2. Инициализация и сохранность

- PostgreSQL в Docker Compose использует именованный том `postgres_data`.
- Hibernate настроен на `ddl-auto: update`: при запуске обновляет структуру без штатного пересоздания всей схемы.
- `src/main/resources/data.sql` содержит демонстрационные данные: 69 печей, четыре машины и связанные примеры настроек/операций/уведомлений/температур.
- Демонстрационные температуры не являются live-телеметрией.
- `docker compose down` останавливает контейнеры, но сохраняет именованный том.
- `docker compose down -v` удаляет том и может привести к потере данных БД; не использовать для обычной остановки.

## 6. Планирование и контроль графика

В коде планировщика присутствуют три алгоритма:

- **B1 FIFO** — базовое последовательное планирование.
- **B2 idle** — вариант планирования с учётом простоев/занятости оборудования.
- **B3 smooth** — вариант, ориентированный на более равномерное распределение операций.

Алгоритмы запускаются на одном входном наборе, а результаты могут сравниваться по вычисляемым метрикам. Версии графика сохраняются в `schedule_runs`, операции — в `schedule_operations`. При пересчёте создаётся новая версия, а предыдущая сохраняется в истории.

В модели операции используются статусы `PLANNED`, `IN_PROGRESS`, `DONE`, `OVERDUE`, `IMPOSSIBLE`. Сохраняются плановые и фактические времена, приоритет, признак ручного изменения и отклонение в минутах.

**Ограничение:** автоматические валидаторы технологических правил в текущем коде покрывают H1 (серийность) и H4 (связь «выдача → загрузка»). Не следует заявлять, что реализована автоматическая проверка полного набора H1–H9. Параметры `holdNotifyMin` и `holdAutoSkipMin` сохраняются, но автоматическая логика HOLD_WARNING и авто-пропуска пока не подключена.

## 7. Docker-развёртывание

В `docker-compose.yml` определены три сервиса:

| Сервис | Контейнер | Порт хоста | Назначение |
|---|---|---:|---|
| `coke-postgres-db` | `coke_factory_database` | 5432 | PostgreSQL 15 |
| `coke-app` | `coke_factory_app` | 8080 | Spring Boot backend |
| `coke-front` | `coke_factory_front` | 5173 | Nginx + frontend |

Backend запускается после прохождения healthcheck PostgreSQL (`pg_isready`). Данные PostgreSQL хранятся в томе `postgres_data`.

### 7.1. Первый запуск в Windows PowerShell

Из корня проекта:

```powershell
Copy-Item .env.example .env
```

Открой `.env`, задай локальное значение `POSTGRES_PASSWORD`, затем выполни:

```powershell
docker compose up --build -d
docker compose ps
```

Адреса:

- Frontend: `http://localhost:5173`
- Backend: `http://localhost:8080`
- Swagger: `http://localhost:8080/swagger-ui.html`
- OpenAPI: `http://localhost:8080/v3/api-docs`

Остановка без удаления БД:

```powershell
docker compose down
```

Полный сброс БД (удаляет данные тома):

```powershell
docker compose down -v
```

Не добавляй реальный `.env` в Git и не используй демонстрационные пароли в production.

Публичный туннель Cloudflare (сервис `tunnel`) по умолчанию не запускается: API без авторизации,
поэтому система публикуется наружу только явно:

```powershell
docker compose --profile tunnel up --build -d
docker compose logs tunnel   # здесь будет ссылка https://...trycloudflare.com
```

### 7.2. Проверка PostgreSQL в запущенном Compose

```powershell
docker compose exec coke-postgres-db sh -lc 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

Ожидаемый результат содержит `accepting connections`.

Список таблиц:

```powershell
docker compose exec coke-postgres-db sh -lc 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\\dt"'
```

## 8. Автоматическое тестирование

В конечном архиве есть несколько уровней тестирования. Они проверяют разные части системы и не заменяют друг друга.

### 8.1. API-контрактные тесты с MockMvc

Файл: `src/test/java/org/example/coke_factory/api/ApiControllerContractTest.java`.

В классе 22 тестовых сценария. Используются реальные контроллеры в standalone MockMvc, а сервисы и репозитории подменяются Mockito-моками. Проверяются HTTP-маршруты и методы, параметры, сериализация, коды ответов, обработка неверных входных данных, делегирование вызовов и экспорт CSV.

Покрываемые группы: оборудование, печи, операции, настройки, уведомления, аудит, температура, прогоны графика, ручная корректировка, CSV-импорт, доступность печей/машин и единый формат ошибок.

**Граница:** эти тесты не проверяют настоящую PostgreSQL, транзакции и корректность JPA-маппинга.

### 8.2. Интеграционные тесты PostgreSQL через Testcontainers

Файл: `src/test/java/org/example/coke_factory/api/PostgresApiIntegrationTest.java`.

В классе три теста. Testcontainers поднимает отдельный временный контейнер `postgres:15-alpine`, а Spring Boot подключается к нему через динамические datasource properties. Используется настоящая PostgreSQL, не H2 и не mock-репозитории.

Проверяется:

1. Подключение к PostgreSQL, наличие таблиц и загрузка демонстрационных данных.
2. Полный CRUD оборудования через HTTP API с последующей проверкой SQL-запросом, что данные действительно сохранены/изменены/удалены.
3. Сохранение и чтение связи между `coke_ovens` и `equipment`.

Для тестовой БД задан `ddl-auto: create-drop`; после тестового класса временный контейнер удаляется. Рабочий том `postgres_data` приложения не используется и не изменяется.

### 8.3. Другие тесты

- Сервисные тесты backend: симуляторный фасад, импорт справочников, логика прогонов графика.
- Тесты `SimulatorStateController` проверяют отдельный HTTP-контракт состояния симулятора.
- Отдельная сборка `simulator/` содержит собственные тесты модели, состояний, серийности, планировщиков и метрик.
- `CokeFactoryApplicationTests` помечен `@Disabled`; вместо него проверка настоящего Spring Boot + PostgreSQL выполняется отдельным `PostgresApiIntegrationTest`.

Требования:

- JDK 21;
- Docker Desktop / Docker Engine запущен;
- доступен Docker image `postgres:15-alpine` (при первом запуске будет скачан);
- Gradle Wrapper может скачать Gradle и зависимости Maven Central при первом запуске.

Windows PowerShell, из корня проекта:

```powershell
.\gradlew.bat test
```

Linux/macOS:

```bash

```

Отдельно можно собрать backend:

```powershell
.\gradlew.bat bootJar
```

Отдельные тесты движка симулятора:

```powershell
cd simulator
.\gradlew.bat test
```

**Важно:** Dockerfile backend собирает JAR с исключением тестов (`-x test`), поэтому успешная сборка Docker-образа сама по себе не означает, что тесты были запущены. Перед демонстрацией/защитой запускай тесты отдельной командой.

### 8.5. Smoke-проверка API в Docker

После запуска Compose:

```powershell
.\scripts\smoke-api.ps1
```

Скрипт выполняет безопасные GET-запросы к OpenAPI и основным read-endpoint'ам. Он проверяет, что приложение доступно по HTTP и базовые маршруты отвечают успешными статусами. Это проверка доступности, а не замена интеграционным тестам.

## 10. Ограничения и дальнейшие улучшения

1. Текущее состояние симулятора находится в памяти backend-процесса. При перезапуске оно не восстанавливается автоматически из PostgreSQL; предусмотрен JSON export/import. Действующий прогон графика, посчитанный для прежнего состояния (перезапуск backend, «Сброс», загрузка снимка, смена seed/схемы, импорт печей), автоматически переводится в архив с записью в журнал — после этого график нужно сформировать заново.
2. Не реализованы аутентификация, авторизация и разграничение ролей.
3. Температурные измерения в начальном SQL — демонстрационные, не потоковая телеметрия.
4. Автоматические валидаторы технологических ограничений покрывают H1 и H4, а не полный перечень H1–H9.
5. `holdNotifyMin` и `holdAutoSkipMin` сохраняются, но автоматические HOLD_WARNING и авто-пропуск не реализованы.
6. Миграции Flyway отсутствуют; используется `ddl-auto: update`.
7. CSV-импорт реализован для печей и машин; импорт всех возможных производственных файлов не заявляется.
8. Новые интеграционные тесты PostgreSQL проверяют конкретные критичные сценарии, а не полный CRUD и все связи каждой сущности.
9. Для production следует ограничить внешний доступ к PostgreSQL, вынести секреты в защищённое хранилище, включить миграции, настроить резервное копирование и мониторинг.

## 11. Краткая версия для защиты

«Backend реализован на Java 21 и Spring Boot 3.4.4. REST API разделяет операции с долговременными данными PostgreSQL и команды динамического симулятора. Для доступа к данным используется Spring Data JPA. В PostgreSQL сохраняются справочники оборудования и печей, операции, версии графика, настройки, уведомления, температурные измерения и аудит. Дополнительно добавлены интеграционные тесты Testcontainers на настоящем PostgreSQL 15: проверяется подключение, CRUD оборудования через REST API и связь печи с оборудованием. Для проверки развёрнутого приложения предусмотрен PowerShell smoke-скрипт. Тесты симулятора остаются в отдельном модуле; его исходный код в рамках API-доработки не менялся».
