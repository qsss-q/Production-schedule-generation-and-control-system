# 09. Актуальный демо-сценарий

Документ описывает сценарий, который соответствует **текущему исходному коду**,
а не планируемым функциям.

## 1. Что можно показать

1. Справочник 69 печей и четырёх машин.
2. Импорт CSV справочника печей и машин; экспорт/импорт JSON-снимка симулятора.
3. Формирование графика B1 FIFO, B2 idle или B3 smooth.
4. Учёт шага, окна смены, доступности оборудования и приоритета.
5. Таймлайн, статусы операций и план/факт.
6. Ручной перенос операции с обязательной причиной.
7. Уведомления о просроченных/невозможных операциях и журнал действий.
8. Сравнение алгоритмов по реализованным метрикам.

## 2. Последовательность демонстрации

### Шаг 1. Запуск и исходные данные

Запустить систему через Docker Compose и открыть `http://localhost:5173`.
Проверить подключение к backend и наличие данных в левой панели.

Начальные демонстрационные данные создаются из `src/main/resources/data.sql`,
если соответствующие таблицы пусты: 69 печей, четыре машины, одна активная
настройка расписания, несколько примерных операций, уведомлений и температурных
измерений. Температурные измерения — статические демонстрационные данные, не
телеметрия симулятора.

### Шаг 2. Настройки графика

В левой панели выбрать:

- алгоритм B1 FIFO, B2 idle или B3 smooth;
- схему серийности 2-1, 5-2 или 9-2;
- шаг между выдачами;
- приоритет новых операций: 1 — обычный, 2 — высокий, 3 — срочный;
- окно смены;
- порог опоздания до статуса `OVERDUE`;
- доступность печей и машин.

Приоритет не меняет жёсткий порядок серийности. Он влияет на порог опоздания:
чем выше приоритет, тем меньше допустимый порог. Окно смены ограничивает время
начала операций; операция длительностью 30 минут должна полностью помещаться
в смену. Окно через полночь пока не поддерживается.

### Шаг 3. Формирование графика

Нажать «Сформировать график». Backend создаёт новый `schedule_run`, сохраняет
операции в `schedule_operations` и устанавливает план в живой симулятор.
Предыдущий рассчитанный прогон переводится в `ARCHIVED`, история не стирается.

Показать шкалу времени: плановые отметки, статусы и отклонения. Нажатие на
операцию, которая ещё не завершена, открывает форму ручного переноса.
Для переноса обязательна причина; операция не может быть перенесена в прошлое
или за пределы активного окна смены.

### Шаг 4. Сравнение алгоритмов

Открыть окно «Алго». Сравнение выполняется на одном снимке состояния и одном seed;
случайные отказы на время офлайн-реплея выключаются, чтобы не смешивать эффект
алгоритма со случайностью.

Показать доступные критерии:

- количество просроченных операций;
- суммарная просрочка;
- равномерность ОЕЭ;
- простой машин и печей;
- максимальная передержка;
- разброс интервалов;
- нарушения проверяемых ограничений.

**Ограничение:** метрика ограничений в текущей версии проверяет только H1
(серийность) и H4 (выдача → загрузка). Она не является валидатором H1–H9.
Сравнение другой схемы серийности доступно через API, но для другой схемы
симулятор пересобирается в стационаре, поэтому это не идентичный снимок состояния.

### Шаг 5. Работа симулятора и отказ

Нажать «Пуск». Симуляция движется с выбранным коэффициентом скорости.
Для демонстрации отказа открыть окно «Сим» и нажать «Сгенерировать отказ».
Сейчас доступно ручное внедрение отказа выталкивания; также конфигурация
симулятора позволяет задавать seed и вероятности случайных отказов.

Это не сценарий с заранее назначенным отказом ровно на 34-й модельной минуте:
такого таймера в текущей реализации нет.

### Шаг 6. План/факт и уведомления

При появлении фактической выдачи сервис синхронизирует `actual_start`,
`actual_end`, `deviation_minutes` и статус операции. Если операция не началась
до окончания планового интервала с учётом настроенного порога, она получает
`OVERDUE`. Если печь недоступна, операция получает `IMPOSSIBLE`.

При превышении порога создаётся запись в `notifications`. Непрочитанные
уведомления отображаются в правой панели; оператор может отметить их прочитанными.
События симулятора и сохранённые уведомления — разные источники данных:
первые живут в памяти симулятора, вторые — в PostgreSQL.

### Шаг 7. Изменение доступности и аудит

Вывести печь из серии или вернуть её через левую панель. Для машин переключить
доступность в блоке оборудования. Эти изменения применяются к справочнику и
живому симулятору, после изменения ревизии активный график пересчитывается.

В таймлайне перенести будущую операцию и указать причину. В правой панели показать
записи аудита. В журнале сохраняются действия симулятора, импорт, формирование
и сравнение прогонов, ручные переносы, изменения настроек, справочников,
статусов и приоритетов операций.

### Шаг 8. Экспорт

- Выгрузить JSON-снимок батареи и при необходимости восстановить его через
  «Восстановить».
- Выгрузить операции активного прогона в CSV.
- Для выгрузки метрик прогона использовать
  `GET /api/v1/schedule-runs/{id}/export.csv?type=metrics`.

## 3. Что важно не обещать комиссии

| Возможность | Текущее состояние |
|---|---|
| B1 FIFO, B2 idle, B3 smooth | Реализованы |
| Версии прогонов и пересчёт после возмущений | Реализованы |
| Ручной перенос операции | Реализован в UI и API |
| Настройка шага и окна смены | Влияют на план |
| Приоритет | Сохраняется у операции; влияет на порог опоздания, не меняет серийность |
| Доступность четырёх типов машин | Реализована; симулятор моделирует по одной машине каждого типа |
| Автоматические уведомления | Создаются для просрочки/невозможной операции |
| `HOLD_WARNING` и авто-пропуск по `holdAutoSkipMin` | Не реализованы; поля политики прогона пока сохраняются, но не управляют симуляцией |
| Проверки H1–H9 | Автоматически проверяются только H1 и H4 |
| Температурная телеметрия | Не реализована; в БД только демонстрационные замеры |
| Несколько батарей | Не поддерживаются; симулятор работает с одной батареей |
| Авторизация и роли | Не реализованы; аудит использует условного пользователя `operator` |
| Полный импорт всех файлов из `docs/04` | Реализованы только CSV печей и машин, JSON-снимок; прочие форматы — спецификация |
