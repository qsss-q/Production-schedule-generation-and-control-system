# 09. Демо-сценарий

Документ фиксирует **что именно показываем**, в каком порядке и по каким признакам
считаем демо состоявшимся. Это не описание системы целиком — только сквозной проход,
который должен быть воспроизводим по кнопке.

---

## 0. Кратко по шагам

1. Загружаем состояние: 69 печей, схема 9-2, П-17 в ремонте, П-44 неисправна, машины доступны.
2. Формируем график B2 — 67 выдач в порядке серий `1→3→5→7→9→2→4→6→8`.
3. Проверяем ограничения H1–H9 — нарушений нет.
4. Пускаем симулятор на скорости x60.
5. На 34-й модельной минуте выталкиватель встаёт на 24 минуты.
6. Операции уходят в `OVERDUE`; на 5-й минуте перестоя приходит уведомление с правом вывести печь из серии.
7. Оператор переносит П-28 и выводит П-44 из серии по уведомлению — обе правки в журнале.
8. Пересчитываем график: новый прогон, прежний остаётся в истории.
9. Запускаем B3 smooth с того же состояния, того же seed и того же отказа.
10. Сравниваем B2 и B3 по критериям ТЗ; B1 — эталонной строкой.
11. Прогоняем победивший алгоритм на схемах 2-1 и 5-2 и сравниваем три схемы.
12. Показываем итог: лучший алгоритм и лучшая схема для текущего состояния батареи.

---

## 1. Цель демо

> Система не рисует график — она строит его разными способами на одном и том же
> состоянии батареи, ломает его отказом оборудования, показывает отклонение от плана
> и доказывает цифрами, какой способ лучше.

Демо идёт по двум осям, и **каждый раз меняется только один параметр**:

| Ось | Что сравниваем | На какой схеме / алгоритме |
|---|---|---|
| Алгоритм | B2 `idle` против B3 `smooth` (B1 — эталон) | обе на схеме 9-2 |
| Серийность | 2-1, 5-2, 9-2 | все на победившем алгоритме |

Целевой результат — **не красивый экран**, а две таблицы сравнения, в которых:

- ноль нарушений серийности во всех строках;
- одинаковый вход у всех прогонов;
- победитель объяснён словами, а не оставлен зрителю.

## 3. Фиксированные данные прогона

Все параметры задаются до старта и **не меняются между прогонами одного сравнения** —
иначе сравнение недействительно.

| Параметр | Значение | Источник |
|---|---|---|
| Батарея | Б-1, 69 печей | `docs/06` |
| Схема серийности | `9-2` для сравнения алгоритмов; `2-1`, `5-2`, `9-2` для сравнения схем | `docs/06` |
| Оборот печи `T_об` | 840 мин | `docs/05` §1.2 |
| Период коксования `T_кокс` | 830 мин | `SimConfig.defaults()` |
| Интервал выдачи `Δt` | 12,17 мин | `840 / 69` |
| Допуск передержки | 5 мин | `SimConfig.defaults()` |
| Начальное состояние | П-17 в ремонте, П-44 неисправна | сценарий |
| Машины | КВ, ДСМ, ТВ, УВ — доступны | сценарий |
| Скриптовый отказ | КВ недоступен 24 мин на модельном времени 34 мин | сценарий |
| Политика удержания | уведомить после 5 мин перестоя; авто-пропуск **выключен** | `docs/05` §1.2, `docs/10` §5.7 |
| Seed | фиксированный, одинаковый для всех прогонов сравнения | `docs/06` |
| Скорость | x60 (1 с = 1 мин) | `SimulatorService` |

> **Важно.** Отказ ставится на **34-й модельной минуте** — это 08:34 при `T0 = 08:00`,
> то есть в начале смены. Так зритель успевает увидеть и срыв, и восстановление
> внутри одного окна демо.

## 4. Сценарий по шагам

Легенда статуса: ✅ есть в коде · 🟡 есть частично · ❌ отсутствует

### Шаг 1. Исходное состояние

| | |
|---|---|
| Действие | Открыть экран «Состояние батареи» |
| На экране | 69 печей, схема 9-2, счётчики по статусам; П-17 — ремонт, П-44 — неисправна; все 4 машины доступны |
| Доказывает | загрузку исходных данных о состоянии оборудования |
| Статус | 🟡 данные есть в `data.sql`, отдельного экрана нет |

Выталкиватель в `data.sql` **доступен** (исправлено 24.11.2026): недоступность
приходит событием `MACHINE_DOWN`, а не стартовым справочником.

### Шаг 2. Формирование графика B2

| | |
|---|---|
| Действие | «Сформировать график», алгоритм `b2_idle` |
| На экране | таймлайн: **67 выдач** (69 минус 2 недоступные), серии идут `1 → 3 → 5 → 7 → 9 → 2 → 4 → 6 → 8` |
| Доказывает | график построен по серийности, а не по номерам печей |
| Статус | ❌ сейчас отдаётся прогноз симулятора, не план |

Подсветить первую серию: `1, 10, 19, 28, 37, 46, 55, 64` — видно шаг 9.

### Шаг 3. Проверка серийности

| | |
|---|---|
| Действие | Нажать «Проверить ограничения» |
| На экране | H1 — выполнено, H2 — выполнено, …; список пуст |
| Доказывает | серийность проверяется кодом, а не глазами |
| Статус | ❌ валидатора H1–H9 нет |

Это дешёвый шаг, но он снимает главный вопрос комиссии: «а вы уверены, что порядок верный?»

### Шаг 4. Пуск симулятора

| | |
|---|---|
| Действие | «Пуск», скорость x60 |
| На экране | печи едут по ленте, статусы `PLANNED → RUNNING → DONE`, машины двигаются вдоль батареи |
| Доказывает | график живой и связан с оборудованием |
| Статус | ✅ симулятор работает |

### Шаг 5. Отказ оборудования

| | |
|---|---|
| Действие | Срабатывает скриптовое событие: **КВ недоступен 24 мин** |
| На экране | событие `critical`, машина помечена как недоступная, ближайшие операции сдвигаются |
| Доказывает | реакцию системы на отказ, а не заученную картинку |
| Статус | ❌ такого события нет, есть только «тугой ход» на 60 мин |

### Шаг 6. План/факт, уведомление и порог удержания

| | |
|---|---|
| Действие | Смотреть ленту и карточку уведомления |
| На экране | операции уходят в `OVERDUE`; на 5-й минуте перестоя приходит уведомление «передержка П-44, 5 мин» с кнопкой «вывести из серии» и причиной («печь не готова» или «КВ занят»); при включённом авто-пропуске на 30-й минуте печь пропускается сама |
| Доказывает | контроль исполнения, порог из нормативов и право оператора решить |
| Статус | 🟡 `OVERDUE` считается, уведомлений нет |

Порог уведомления — допуск 5 мин; порог авто-пропуска — 30 мин (`maxInterval`), по умолчанию
**выключен**. Пока он выключен, решение принимает оператор.

Система обязана показать, **поможет ли пропуск**: если печь блокирует машина, а не сама печь,
пропуск ничего не ускорит, и кнопка должна быть недоступна с объяснением. Иначе оператор
выкинет печь «на всякий случай» и потеряет кокс зря.

### Шаг 7. Ручная корректировка

| | |
|---|---|
| Действие | Перенести П-28 на свободное окно; по уведомлению вывести П-44 из серии («неисправность») |
| На экране | операция сдвинулась и помечена как ручная; печь вне серии; в журнале две записи |
| Доказывает | оператор может вмешаться, и это зафиксировано |
| Статус | 🟡 `PUT /operations/{id}` есть, «вывести из серии» и UI — нет |

В журнале должно быть: кто, что, когда, было/стало, причина.

«Не выгружать» — это не удаление строки, а исключение печи из серии. Механика, модель данных,
API и задачи для команды — в [`10-исключение-печей.md`](10-исключение-печей.md). Для сценария
важно одно: исключение — **вход нового прогона**, поэтому шаг 8 обязателен, а `RUN-1`
остаётся неизменным.

### Шаг 8. Пересчёт графика

| | |
|---|---|
| Действие | «Пересчитать» |
| На экране | новый прогон `RUN-2`, старый `RUN-1` остался в истории |
| Доказывает | пересчёт не затирает предыдущий график |
| Статус | ❌ сущности прогона нет, старые операции удаляются |

Сейчас `ScheduleService` делает `deleteByManualFalse()` — история уничтожается. Без
версий шаг 9 невозможен.

### Шаг 9. Второй алгоритм на том же входе

| | |
|---|---|
| Действие | «Сформировать B3» — **повторный прогон с того же начального состояния**, тот же seed, тот же отказ |
| На экране | `RUN-3`, те же 67 выдач в том же порядке, но другие времена |
| Доказывает | сравнение честное: порядок не менялся, отличается только распределение долга |
| Статус | ❌ B3 отсутствует |

B2 догоняет залпом — несколько коротких интервалов, потом ровно. B3 размазывает тот же
запас восстановления по остатку прохода. Порядок печей у обоих один и тот же.

Ключевое: это **replay**, а не второй экран рядом. Оба прогона стартуют из одной точки
и проходят один и тот же сценарий отказов.

### Шаг 10. Сравнение алгоритмов

| | |
|---|---|
| Действие | «Сравнить RUN-1 и RUN-3» |
| На экране | B2 против B3 по критериям ТЗ плюс M8 (разброс интервалов) и M9 (макс. передержка); строкой ниже — B1 эталон; победитель подсвечен |
| Доказывает | обязательное требование кейса, причём сравнение содержательное: ни один не лучше по всем критериям |
| Статус | ❌ нет |

B1 показывается серой строкой как база: он не участвует в выборе, но без него непонятно,
сколько стоит гибкость. B2 выигрывает темпом, B3 — тепловым режимом; если замер покажет
иначе, показываем как есть.

Победивший алгоритм дальше используется как единственный — иначе на шаге 11 мы будем
менять два параметра сразу и сравнение схем ничего не докажет.

### Шаг 11. Выбор серийности

| | |
|---|---|
| Действие | «Сменить схему»: тот же победивший алгоритм прогоняется на `2-1` и `5-2` → `RUN-4`, `RUN-5` |
| На экране | три строки `2-1 / 5-2 / 9-2`, те же критерии ТЗ плюс число серий и число деградированных серий |
| Доказывает | серийность — параметр планировщика, и его выбор доказуем, а не задан заранее |
| Статус | ❌ нет |

Из-за смены схемы меняется порядок выдачи, поэтому это **новый прогон с того же состояния**,
а не правка текущего. Сравнивать между схемами можно только метрики, не зависящие от числа
серий: просрочку, простой, равномерность; число серий показываем справочно.

## 6. Критерии приёмки демо

Демо состоялось, если:

1. график строит реальный алгоритм, а не прогноз симулятора;
2. порядок выдачи соответствует выбранной схеме и это проверено тестом, а не глазами;
3. отказ воспроизводим: фиксированный seed и скриптовое событие;
4. все прогоны лежат в базе одновременно и имеют идентификаторы;
5. метрики считаются из данных, а не вбиты в UI;
6. ручная правка и журнал работают хотя бы для двух действий — перенос и вывод печи из серии;
7. на экране сравнения нет ни одного числа, которое нельзя пересчитать из базы;
8. схемы сравниваются на одном алгоритме и одном состоянии — иначе результат недействителен;
9. весь проход занимает **не больше 9 минут**.

## 7. Что нужно доделать, чтобы сценарий собрался

### Блокирующее

**1. Событие простоя машины с длительностью.**
Сейчас есть только тугой ход на 60 мин внутри выдачи. Нужно
`MACHINE_DOWN { machine, from, duration }`, иначе шаг 5 показать нечем.

**2. План как вход симулятора.**
Сейчас `planned = k · Δt` — внутренняя сетка симулятора, а не наш график. Пока это так,
«пересчитать график» ничего не меняет, и план/факт сравнивает систему саму с собой.

**3. Сущность прогона.**
`ScheduleRun` с алгоритмом, схемой, входом, seed и метриками; `run_id` у операций. Без неё
нет ни версий, ни сравнения.

**4. Схема как параметр прогона.**
`2-1` / `5-2` / `9-2` должны быть входом планировщика, а не константой. Построение порядка
уже есть в `simulator/Seriality`, его нужно переиспользовать, а не писать заново.

**5. Политика удержания и порог пропуска.**
`holdNotifyMin` (по умолчанию 5 мин перестоя) и `holdAutoSkipMin` (по умолчанию 30 мин,
авто-пропуск выключен), событие `HOLD_WARNING`, уведомление с кнопкой «вывести из серии»,
настройка авто-пропуска. Без этого шаг 6 показать нечем. Детали — `docs/10` §5.7.

### Поддерживающее

**6. Ограничение минимального интервала и учёт перестоя.**
Сейчас симулятор нагоняет поток за счёт кинематики машин (~9,7 мин между выдачами) и не
знает ни предела форсирования (≈ 8,7 мин), ни того, что готовность печи сама ограничивает
восстановление (замерено 3 мин/оборот). Если не ограничить, B2 и B3 будут выглядеть лучше,
чем есть. Предел — не параметр «с потолка», а следствие `readyAt` и `minInterval`;
B2 и B3 отличаются только способом потратить один и тот же запас.

### Замеренное поведение, которое надо учесть в сценарии

- запас батареи — **3 минуты на оборот** (`840 − 830 − 2 − 5`), то есть 0,4 %;
- один тугой ход на 60 мин даёт задержку **+57,5 мин** и гасится по **3 мин за оборот**;
- полное восстановление — **21 оборот ≈ 12 суток** модельного времени;
- отказ обогрева на 30 мин сдвигает готовность печи ровно на 30 мин и даёт
  задержку выдачи **+27 мин** (30 − запас 3); гасится так же — по 3 мин за оборот.
  До 24.11.2026 отказ в середине коксования не влиял на готовность вовсе —
  исправлено и зафиксировано тестами `heatFaultMidCoking…` и `singleJam…`.

Первые три числа и скорость восстановления фиксируются тестами
`SimulatorTest` (не подгоняются): `singleJam_delay57AndHalf_andRecovery3MinPerCycle`
и `machineKinematics_respectForcingFloor` (пол форсирования 8,7 мин из [05] §9).

Отсюда два следствия для демо:

1. окно демо — **не больше 1–2 оборотов**, иначе статистика утонет в фазовом долге;
2. отказ надо ставить **в начало окна**, чтобы зритель успел увидеть и срыв, и восстановление.

## 8. Регламент повторяемости

1. `POST /simulator/control {action: reset}` — детерминированный старт.
2. Загрузить исходное состояние (П-17, П-44, машины) — файлом снимка:
   `GET /simulator/state/export` на 0-й минуте, поправить, `POST /simulator/state/import`
   ([03](03-контракт-api.md) §8, формат — [04](04-форматы-файлов.md) §10).
   Этот же файл — точка возврата для шага 8.
3. `POST /schedule-runs {algorithm: b2_idle, seriality: "9-2", seed, holdPolicy}` → `RUN-1`.
4. `POST /simulator/control {action: start}`, скорость x60.
5. По достижении модельной минуты 34 — событие `MACHINE_DOWN`.
6. Дать пройти 60–90 модельных минут; дождаться `HOLD_WARNING` по П-44.
7. Ручные правки (перенос П-28, вывод П-44), пересчёт → `RUN-2`.
8. Вернуть состояние батареи из файла шага 2, затем `POST /schedule-runs {algorithm: b3_smooth, seriality: "9-2", seed, holdPolicy}` → `RUN-3`.
9. `POST /schedule-runs/compare {runs: [RUN-1, RUN-3], reference: RUN-0}` — ось «алгоритм».
10. `POST /schedule-runs {algorithm: b3_smooth, seriality: "5-2", seed, holdPolicy}` → `RUN-4`.
11. `POST /schedule-runs {algorithm: b3_smooth, seriality: "2-1", seed, holdPolicy}` → `RUN-5`.
12. `POST /schedule-runs/compare {runs: [RUN-3, RUN-4, RUN-5]}` — ось «серийность».

`holdPolicy` — `{notifyAfterMin: 5, autoSkipAfterMin: 0}`: уведомление включено, авто-пропуск
выключен. `RUN-0` — базовый прогон `b1_fifo`, он нужен только как эталонная строка.

Любое отклонение от шагов 1–2 делает сравнение недействительным. Шаги 10–11 выполняются
**тем же алгоритмом**, что победил на шаге 9, иначе сравнение схем смешивает две переменные.

## 9. Что говорить на защите

1. «Серийность — жёсткое ограничение, а не пожелание. Ни один алгоритм и ни одна схема её
   не нарушают: по H1 ноль нарушений во всех строках.»
2. «Мы сравниваем на одном входе: то же состояние, тот же seed, тот же отказ.»
3. «B2 гасит долг залпом: несколько коротких интервалов, и поток в норме. B3 размазывает
   тот же долг по остатку прохода и не рвёт ритм.»
4. «B1 — эталон. Мы его не выбираем, но без него непонятно, сколько стоит гибкость.»
5. «Сначала выбираем алгоритм на схеме 9-2, потом схему на победившем алгоритме — иначе
   сравнение смешивает две переменные.»
6. «Когда печь перестаивает дольше допуска, оператор получает уведомление и право вывести
   её из серии. Авто-пропуск можно включить на 30-й минуте, но по умолчанию решает человек.»
7. «Пропуск не переставляет печи: он вырезает одну, остальные идут в свои слоты.
   Поэтому H1 остаётся целым.»
8. «Батарея заполнена на 99,6 %, поэтому запас на восстановление — 3 минуты за оборот.
   Это ограничивает любой алгоритм и любую схему: чем меньше запас, тем меньше выигрыш.»
9. «Мы не подгоняли цифры: там, где B2 или 9-2 не выигрывают, мы это показываем.»

## 10. Риски

| Риск | Реакция |
|---|---|
| B2 или B3 не выигрывает | показать честно и объяснить через запас батареи |
| B2 и B3 идут вровень | это тоже результат: при 3 мин запаса разница мала |
| Оператор пропускает печь зря | кнопка недоступна, если блокирует машина, а не печь |
| Авто-пропуск режет поток | по умолчанию выключен; включается только на демо-стенде |
| 9-2 проигрывает другой схеме | показать честно: это результат, а не повод крутить цифры |
| Схемы имеют разное число серий | сравнивать только метрики, не зависящие от числа серий |
| Фазовый долг красит статистику | ограничить окно 1–2 оборотами, отказ — в начало |
| Данные прогонов разъехались | сравнение запрещено, прогон пересоздаётся |
| Симулятор нагоняет быстрее нормы | ввести предел восстановления до демо, иначе цифры завышены |
| Не хватает времени | режем шаги 3 и 7, но не шаги 10–11 — оба сравнения обязательны |
