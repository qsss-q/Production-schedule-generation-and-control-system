# 10. Исключение печей из серии

Документ описывает ручное выведение печи из серии: семантику, изменения в симуляторе,
модель данных, API и задачи для команды. Автоматический пропуск (когда планировщик сам
решает не выдавать печь) использует тот же механизм — различается только инициатор.

---

## 1. Зачем это нужно

Серийность фиксирует **порядок**, но не гарантирует, что каждая печь физически может быть
выдана. Причины вывести печь из серии:

- печь неисправна или в ремонте;
- кокс не готов, а ждать нельзя;
- срочный заказ требует не задерживать остальные печи;
- технологическое решение оператора.

Без этого механизма поток либо стоит, либо его приходится ломать перестановкой — а это уже
нарушение H1. Исключение — легальный способ продолжить работу, заплатив одной печью.

---

## 2. Термины

| Термин | Значение | Кто инициирует |
|---|---|---|
| **Пропуск** (`skip`) | Планировщик не выдаёт печь в текущем проходе | алгоритм |
| **Исключение** (`exclusion`) | Оператор выводит конкретную печь из серии | оператор |
| **Возврат** (`return`) | Печь снова попадает в поток | политика прогона |
| **Вне серии** (`OUT_OF_SERIES`) | Состояние печи, пока она исключена | — |
| **Ремонт** (`REPAIR`) | Состояние оборудования, не решение планировщика | инженер |

Пропуск и исключение — **одно и то же с точки зрения механики**. Отличаются инициатор,
причина и запись в журнале.

---

## 3. Инварианты

1. Исключение **вырезает** печь из порядка, а не переставляет остальные. Относительный
   порядок сохраняется, H1 не нарушается.
2. Исключение **не ускоряет поток**. Следующая печь идёт в свой плановый слот, потому что
   её кокс ещё не готов.
3. Времена остальных печей **не меняются** — иначе поедут `readyAt` и начнётся H2.
4. Исключение — это **вход прогона**, а не правка его результата. Новое решение = новый
   `SCHEDULE_RUN`.
5. Исключённая печь **не исчезает**: кокс греется, перестой растёт, сорт падает.
6. Число исключённых печей — **отдельная метрика**. Ими нельзя улучшать просрочку.
7. Лимит — **не больше 2 печей за проход**. Дальше это уже не серия: `INFEASIBLE`.

---

## 4. Два независимых состояния

Смешивать их нельзя — от этого зависит и логика, и интерфейс.

| Состояние | Где живёт | Что значит | Горизонт |
|---|---|---|---|
| `REPAIR` | оборудование | печь физически недоступна | до даты ремонта |
| `OUT_OF_SERIES` | планирование | печь пропущена в проходе | проход или до даты |

Печь в ремонте **всегда** вне серии. Печь вне серии **не обязательно** в ремонте.

В симуляторе ремонт — это отсутствие выдачи по физической причине, исключение — отсутствие
выдачи по решению. Для расчёта расписания важен только итог: «в этом проходе печь не
выдаётся».

---

## 5. Симулятор: что менять

### 5.1 Состояние

Сейчас `Simulator` не умеет пропускать: `nextIssue` всегда идёт по порядку, а неготовая печь
просто тормозит поток. Добавляем:

```java
// ru.evraz.koks.sim.Simulator

private final boolean[] outOfSeries;      // печь исключена прямо сейчас
private final int[]     excludedPass;     // проход, в котором пропустить (-1 = нет)
private final double[]  excludedUntil;    // исключение до момента (0 = нет)
private final String[]  exclusionReason;  // причина для события и журнала
private final boolean[] holdWarned;       // уведомление по печи уже отправлено
private int consecutiveSkips;             // защита от пустого прохода
private int skippedCount;                 // сколько слотов потеряно на пропусках
```

И в `OvenState`:

```java
OUT_OF_SERIES("вне серии")
```

И в `Event.Type` — два новых типа, чтобы лента и журнал не собирали их из текста:

```java
EXCLUDED,      // печь выведена из серии
INCLUDED,      // печь снова в серии
HOLD_WARNING   // перестой превысил holdNotifyMin — оператору пора решать
```

### 5.2 Публичный API движка

```java
public void excludeOven(int ovenNo, ExclusionScope scope, double untilMin, String reason) {
    checkOven(ovenNo);
    if (outOfSeries[ovenNo]) return;               // идемпотентно
    if (scope == UNTIL && untilMin <= simMin)
        throw new IllegalArgumentException("исключение до момента в прошлом");

    outOfSeries[ovenNo] = true;                    // состояние меняется сразу
    exclusionReason[ovenNo] = reason;
    if (scope == PASS) {
        int pass = nextIssue / order.length;
        int consumed = nextIssue % order.length;   // сколько слотов прохода уже пройдено
        int idx = indexOf(order, ovenNo);
        // печь уже прошла свой слот в этом проходе → исключение действует со следующего
        excludedPass[ovenNo] = idx < consumed ? pass + 1 : pass;
    } else {
        excludedUntil[ovenNo] = untilMin;
    }
}

public void includeOven(int ovenNo) {
    checkOven(ovenNo);
    if (!outOfSeries[ovenNo]) return;
    outOfSeries[ovenNo] = false;
    excludedPass[ovenNo] = -1;
    excludedUntil[ovenNo] = 0;
    events.add(new Event(m(simMin), Event.Type.INCLUDED, ovenNo, "печь возвращена в серию вручную"));
}

/** Печи, которые сейчас вне серии — для DTO, UI и метрик. */
public List<Integer> excludedOvens() {
    List<Integer> out = new ArrayList<>();
    for (int p = 1; p <= cfg.ovenCount(); p++) if (outOfSeries[p]) out.add(p);
    return out;
}
```

`excludeOven` не пересчитывает порядок. Она только помечает печь; событие `EXCLUDED` пишется
в `advance`, когда до печи доходит очередь — иначе в ленте событие окажется раньше, чем
операция, которую оно отменяет.

`state()` показывает `OUT_OF_SERIES` сразу после вызова, ещё до слота: для оператора печь
вне серии с момента решения, а не с момента, когда до неё дошёл конвейер.

`skippedCount()` — число **пропусков** (событий `EXCLUDED`), а не число печей, которые сейчас
вне серии. За проход одна и та же печь может быть пропущена дважды, если её исключили дважды
(`PASS`, затем `UNTIL`); для метрик это две разные потери слота.

### 5.3 Алгоритм `advance`

Пропуск встаёт в тот же цикл выбора ближайшего события, что и отказы. Иначе можно
«перепрыгнуть» отказ обогрева, который случится раньше слота.

```java
while (true) {
    expireExclusions();                      // снять истёкшие PASS/UNTIL
    int pass = nextIssue / order.length;
    int p = order[nextIssue % order.length];
    double planned = (nextIssue + 1) * deltaMin;

    double tDischarge = pushStartFor(p, planned);
    double tHeat = ...;
    double tRec  = ...;
    double tSlot = Math.max(planned, simMin);       // слот не раньше текущего момента
    double tSkip = isExcludedAt(p, pass, tSlot) ? tSlot : Double.MAX_VALUE;

    double tNext = Math.min(tDischarge, Math.min(tHeat, Math.min(tRec, tSkip)));
    if (tNext > target) break;

    if (tSkip <= tDischarge && tSkip <= tHeat && tSkip <= tRec) {
        events.add(new Event(m(tSkip), Event.Type.EXCLUDED, p,
                "печь вне серии: " + exclusionReason[p]));
        skippedCount++;
        simMin = m(tSkip);
        nextIssue++;
        if (++consecutiveSkips >= order.length) {
            events.add(new Event(m(tSkip), Event.Type.FAULT, p, "проход пуст: все печи вне серии"));
            break;
        }
        continue;
    }

    consecutiveSkips = 0;
    // ... существующая логика: recovery / heat fault / discharge
}
```

Почему `planned` не пересчитывается: `nextIssue` уже сдвинут на единицу, поэтому следующая
печь автоматически получает **своё** плановое время `(nextIssue+1)·Δt`. Никакого сдвига
остальных не происходит — это и требуется.

### 5.4 Возврат

| Scope | Поле | Когда снимается |
|---|---|---|
| `PASS` | `excludedPass[p] = pass` | при смене прохода, т.е. когда `nextIssue % order.length == 0` |
| `UNTIL` | `excludedUntil[p] = untilMin` | когда `simMin >= excludedUntil[p]` |

```java
/** Исключена ли печь p в проходе pass на момент t. */
private boolean isExcludedAt(int p, int pass, double t) {
    if (!outOfSeries[p]) return false;
    if (excludedUntil[p] > 0) return t < excludedUntil[p];
    return excludedPass[p] == pass;
}

/** Снять истёкшие исключения; вызывать в начале каждой итерации advance. */
private void expireExclusions() {
    int pass = nextIssue / order.length;
    for (int p = 1; p <= cfg.ovenCount(); p++) {
        if (!outOfSeries[p]) continue;
        boolean expired = excludedUntil[p] > 0
                ? simMin >= excludedUntil[p]
                : excludedPass[p] < pass;
        if (expired) {
            double t = excludedUntil[p] > 0 ? excludedUntil[p] : simMin;
            outOfSeries[p] = false;
            excludedUntil[p] = 0;
            excludedPass[p] = -1;
            events.add(new Event(m(t), Event.Type.INCLUDED, p, "печь снова в серии"));
        }
    }
}
```

`outOfSeries[p]` снимается здесь, а не в `doDischarge`: печь может вернуться в серию, так и
не будучи выданной (например, исключение `UNTIL` закончилось, а слот уже прошёл). Выдача —
следствие, а не причина снятия отметки.

Ещё два места:

- `doDischarge` очищает `outOfSeries[p]` после выдачи, чтобы отметка не «залипла», если
  исключение было снято раньше;
- `excludedUntil[p] = 0` выставляется при выдаче — иначе повторная выдача унаследует чужой
  срок.

Перестой не нужно считать отдельно: при возврате `pushStart − readyAt` даст фактическую
величину, и существующая ветка `OVERHOLD` её зафиксирует.

### 5.5 Состояние и прогноз

```java
public OvenState state(int ovenNo) {
    if (t < heatRecoverAt[ovenNo]) return OvenState.FAULT;   // авария важнее
    if (outOfSeries[ovenNo])       return OvenState.OUT_OF_SERIES;
    if (dischargeAt[ovenNo] <= t && t < loadDoneAt[ovenNo]) return OvenState.EMPTY;
    if (t < readyAt[ovenNo])       return OvenState.COKING;
    return (t - readyAt[ovenNo] > cfg.toleranceMin()) ? OvenState.OVERHOLD : OvenState.READY;
}
```

`forecast(limit)` должен **пропускать** исключённые печи и не включать их в план. Иначе
график покажет печь, которую никто не собирается выдавать.

Важно: пропуск не сдвигает `planned` остальных. Индекс `idx = nextIssue + k` считается по
исходному порядку, поэтому исключённая печь «выпадает» из списка, а следующая сохраняет
**свой** слот `(idx + 1)·Δt`. Если считать слоты по позиции в отфильтрованном списке,
времена поедут и H2 начнёт нарушаться на ровном месте.

```java
public List<PlannedDischarge> forecast(int limit) {
    List<PlannedDischarge> out = new ArrayList<>(limit);
    int k = 0;
    while (out.size() < limit && k < order.length) {
        int idx = nextIssue + k++;
        int p = order[idx % order.length];
        int pass = idx / order.length;
        double planned = (idx + 1) * deltaMin;      // слот от индекса, не от позиции в списке
        if (isExcludedAt(p, pass, Math.max(planned, simMin))) continue;  // вне серии — не в план
        double start = out.isEmpty() ? pushStartFor(p, planned) : Math.max(planned, readyAt[p]);
        out.add(new PlannedDischarge(p, planned, readyAt[p], start));
    }
    return out;
}
```

### 5.6 Защиты

| Ситуация | Поведение |
|---|---|
| Печь уже выдана в этом проходе | исключение применяется со следующего прохода + предупреждение |
| Исключают все печи прохода | событие «проход пуст», `advance` останавливается |
| Печь пуста и ждёт загрузки | исключение разрешено, но выдавать нечего — предупреждение |
| Печь в ремонте | исключение разрешено и дублирует ремонт, вреда нет |
| Повторное исключение | идемпотентно, без второго события |

### 5.7 Политика удержания: уведомление и порог пропуска

Печь не выдаётся по двум разным причинам, и они требуют разных действий:

| Причина | Виноват | Поможет ли пропуск |
|---|---|---|
| печь не готова или в аварии | печь | да: остальные пойдут в свои слоты |
| занята машина (КВ, ДСМ, ТВ, УВ) | машина | нет: следующая печь ждёт ту же машину |

Смешивать их нельзя: если предлагать пропуск при занятой машине, оператор выкинет печь,
а поток не ускорится. Система обязана показать причину и, если пропуск бесполезен,
заблокировать кнопку с объяснением.

**Три ступени:**

| Ступень | Условие | Что происходит |
|---|---|---|
| держать | `pushStart − readyAt ≤ holdNotifyMin` | тишина, штатная работа |
| уведомить | `pushStart − readyAt > holdNotifyMin` | событие `HOLD_WARNING`, уведомление с кнопкой «вывести из серии» |
| пропустить | решение оператора **или** `> holdAutoSkipMin` при включённом авто-пропуске | `EXCLUDED`, причина `HOLD_TIMEOUT` |

Параметры прогона:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `holdNotifyMin` | 5 (`toleranceMin`) | через сколько минут перестоя оператор узнаёт |
| `holdAutoSkipMin` | 30 (`maxInterval`); `0` = выключено | через сколько печь пропускается сама |
| `autoSkipOnlyWhenOvenLate` | `true` | не пропускать, если виновата машина |

Авто-пропуск по умолчанию **выключен**: по ТЗ решение принимает оператор, автоматика — это
настройка для стенда и для случая, когда оператора физически нет у пульта.

```java
// в advance: два новых кандидата в общий min()
double tWarn = holdWarned[p] ? Double.MAX_VALUE : readyAt[p] + holdNotifyMin;
double tAuto = autoSkipEnabled && ovenIsLate(p, planned)
        ? readyAt[p] + holdAutoSkipMin
        : Double.MAX_VALUE;

if (tWarn <= tDischarge && tWarn <= tHeat && tWarn <= tRec && tWarn <= tAuto) {
    events.add(new Event(m(tWarn), Event.Type.HOLD_WARNING, p,
            "передержка %.0f мин, причина: %s".formatted(tWarn - readyAt[p], blockReason(p))));
    holdWarned[p] = true;
    simMin = m(tWarn);
    continue;
}
```

`ovenIsLate(p, planned)` = `readyAt[p] > planned`: печь сама не успела к слоту. Если печь готова,
а занята машина, авто-пропуск не срабатывает — это была бы потеря кокса без выигрыша.

Авто-пропуск идёт тем же путём, что ручной: `excludeOven(p, PASS, …)` с причиной
`HOLD_TIMEOUT`. В журнале отличается только инициатор: `SYSTEM` вместо оператора. Это
важно: метрики и события не должны зависеть от того, кто нажал кнопку.

Авто-пропуск подчиняется тому же лимиту, что и ручной: не больше 2 печей за проход.
Если лимит исчерпан, автоматика останавливается и уведомляет — дальше решает оператор
или мастер. Иначе настройка легко превращается в «выкинуть полсерии и выиграть сравнение».

`holdWarned[p]` сбрасывается после выдачи и при смене прохода — иначе повторные уведомления
превратятся в шум.

Уведомление обязано нести признак `helpful`: `true`, если блокирует печь, `false`, если машина.
Фронт по нему включает или блокирует кнопку.

## 6. Backend: модель данных

### 6.1 Новые сущности

```java
@Entity @Table(name = "schedule_runs")
class ScheduleRun {
    UUID id;
    UUID parentId;                 // от какого прогона получен

    String seriality;              // 2-1 | 5-2 | 9-2

    LocalDateTime periodStart;
    Integer holdNotifyMin;         // 5 по умолчанию
    Integer holdAutoSkipMin;       // 0 = авто-пропуск выключен

    RunStatus status;              // DRAFT | CALCULATED | ARCHIVED

    LocalDateTime createdAt;
}

@Entity @Table(name = "schedule_exclusions")
class ScheduleExclusion {
    Long id;
    UUID runId;
    Integer ovenNumber;
    String scope;                  // PASS | UNTIL
    LocalDateTime until;
    String reason;                 // REPAIR | FAULT | HOLD_TIMEOUT | URGENT_ORDER | TECHNOLOGICAL
    String actor;                  // OPERATOR | SYSTEM (авто-пропуск)
    String comment;
    String createdBy;
    LocalDateTime createdAt;
}
```

### 6.2 Изменения существующих

- `ScheduleOperation`: `runId`, `exclusionReason`; `OperationStatus` дополняется `CANCELLED`.
- `entity/OvenState`: добавить `OUT_OF_SERIES` (сейчас `COKING, READY, PUSHING, REPAIR`).
- `ScheduleService.generate`: **убрать** `deleteByManualFalse()`, создавать новый прогон.
- `Notification`: поля `ovenNumber`, `runId`, `action` (`EXCLUDE_OVEN`), `helpful`; в
  `NotificationType` добавить `OVERHOLD`. Сейчас сущность не знает ни печи, ни действия,
  поэтому кнопку в уведомлении сделать не из чего.
- `ScheduleSettings`: `urgentPriority` и значение `URGENT_FIRST` больше не нужны — их место
  занимают `holdNotifyMin`, `holdAutoSkipMin`, `autoSkipOnlyOvenLate`; значение алгоритма
  `SMOOTH` вместо `URGENT_FIRST`. Ручка «приоритетность срочных заказов» переезжает
  в план выпуска (H9), а не в порядок печей (`docs/05` §5).
- `docs/02` привести к фактическим enum'ам.

### 6.3 Сервисы

| Сервис | Ответственность |
|---|---|
| `ScheduleRunService` | создать прогон, пересчитать, сравнить, посчитать `inputHash` |

| `MetricsService` | M1–M9, `skipped`, `excluded` |

## 7. API

### 7.1 Основной сценарий

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/schedule-runs` | создать прогон: `{algorithm, seriality, seed, periodStart, exclusions[], holdPolicy}` |
| `GET` | `/api/v1/schedule-runs/{id}` | прогон + метрики |
| `GET` | `/api/v1/schedule-runs/{id}/operations` | операции прогона |
| `POST` | `/api/v1/schedule-runs/{id}/exclusions/preview` | сухой прогон, вернуть `ExclusionConsequences` |

| `GET` | `/api/v1/settings/hold-policy` | `{notifyAfterMin, autoSkipAfterMin, onlyOvenLate}` |
| `PUT` | `/api/v1/settings/hold-policy` | изменить пороги, запись в журнал |

> Имена в API короче, чем в сущности: `notifyAfterMin` ↔ `holdNotifyMin`,
> `autoSkipAfterMin` ↔ `holdAutoSkipMin`, `onlyOvenLate` ↔ `autoSkipOnlyOvenLate`.
> Маппинг держим в одном месте (DTO), чтобы не разъехался `inputHash`.

### 7.2 Операторское действие целиком

```http
POST /api/v1/operator-actions/exclude-oven
{
  "runId": "…",
  "ovenNumber": 28,
  "scope": "PASS",
  "reason": "HOLD_TIMEOUT",
  "notificationId": "…",
  "comment": "передержка 17 мин, КВ освободится позже"
}
```

Ответ — новый прогон и запись в журнале. Внутри одной транзакции:

1. `ExclusionService.validate` → 409, если есть блокирующие замечания;
2. `ScheduleRunService.createChildRun` — новый `RUN-N` с исключением во входе;
3. `SimulatorService.excludeOven` — чтобы факт совпал с планом;
4. `NotificationService.close(notificationId)` — уведомление закрывается действием;
5. `AuditService.log` — кто, когда, причина, было/стало.

Разделять 2 и 3 нельзя: иначе план и симулятор разъедутся, и это будет выглядеть как срыв
графика, которого не было.

Если `reason = HOLD_TIMEOUT` и действие пришло не от оператора, а от авто-пропуска,
транзакция та же, но `actor = SYSTEM`; отдельного эндпоинта для автоматики нет.

### 7.3 Ошибки

| Код | Когда |
|---|---|
| `409 EXCLUSION_LIMIT` | больше 2 печей за проход |
| `409 OVEN_ALREADY_DISCHARGED` | печь уже выдана, применимо только со следующего прохода |
| `409 SERIES_EMPTY` | исключение опустошает серию |
| `409 INPUT_MISMATCH` | сравнение прогонов с разным `inputHash` |
| `422 OVEN_EMPTY` | в печи нет кокса |

## 8. Интерфейс

### 8.1 Карточка печи

Действие «Вывести из серии» в контекстном меню. Доступно, если печь не пуста.

### 8.2 Модалка подтверждения

Не «вы уверены?», а последствия:

```
Исключить П-28 из серии 1?
  серия 1:        8 → 7 печей
  выдач в проходе: 67 → 66
  план выпуска:   −38 т
  перестой П-28:  с 08:36
  возврат:        следующий проход, около 22:36

Причина: [срочный заказ ▾]   Комментарий: [……]
[Отмена]  [Исключить]
```

Кнопка неактивна, пока `preview` не вернул пустой список `warnings`.

### 8.3 Уведомление о передержке

Приходит карточкой в ленту и в колокольчик, **один раз на печь за проход**:

```
⚠ Передержка П-44 — 7 мин (допуск 5)
   причина: печь не готова, кокс перестаивает
   [Вывести из серии]  [Отложить]
```

Если блокирует машина, текст другой и кнопка недоступна:

```
⚠ Передержка П-44 — 9 мин
   причина: занят КВ, пропуск печи не ускорит поток
   [Вывести из серии] (недоступно)
```

Откладывание не снимает уведомление навсегда: повторно оно не всплывает, но остаётся
в списке до выдачи печи.

### 8.4 Настройка авто-пропуска

В настройках прогона два поля и один переключатель:

```
Уведомлять о передержке через   [ 5 ] мин
Пропускать автоматически через  [30 ] мин   (0 — не пропускать)
Только если печь сама опоздала   [x]
```

Поля подписаны источником нормы (`допуск 5`, `maxInterval 30`), чтобы значение можно было
оспорить, а не принять на веру. Изменение пишется в журнал.

### 8.5 Отображение

- печь в `OUT_OF_SERIES` — оранжевая, серая заливка, бейдж «вне серии»;
- в легенде — отдельный счётчик;
- в ленте — события `EXCLUDED`, `INCLUDED`, `HOLD_WARNING` с причиной;
- в сравнении — колонка «исключено», всегда рядом с просрочкой.

### 8.6 Журнал

Строка: кто, когда, печь, причина, горизонт, было/стало, решение о возврате. Для
авто-пропуска в поле «кто» стоит `SYSTEM` и номер правила, которое сработало.

## 9. Честность сравнения

Исключение уменьшает число выдач, а значит и просрочек. Если это не учитывать, появится
способ «улучшить» метрики, выкинув неудобные печи. Поэтому:

1. `inputHash` включает список исключений — сравнение прогонов с разным набором запрещено
   на оси «алгоритм».
2. В таблице сравнения всегда есть колонки «исключено» и «план выпуска».
3. `MetricsService` считает `skipped` и `excluded` отдельно, они не входят в M1.
4. Прогон с исключениями помечается в отчёте.

## 12. Крайние случаи

| Случай | Ожидание |
|---|---|
| Исключают следующую печь | пропуск в её слот, остальные без изменений |
| Исключают уже выданную печь | применяется со следующего прохода + предупреждение |
| Исключают всю серию | 409 `SERIES_EMPTY` |
| Исключают все печи прохода | проход пуст, планировщик возвращает `INFEASIBLE` |
| Исключают пустую печь | 422 `OVEN_EMPTY` |
| Исключают печь в ремонте | разрешено, идемпотентно |
| Отменяют исключение | новый прогон, история сохранена |
| Два оператора одновременно | оптимистичная блокировка по `runId`, второй получает 409 |
| Сравнивают прогоны с разными исключениями | 409 `INPUT_MISMATCH` |
| Исключение ломает план выпуска | предупреждение, не блокировка |
| Печь опоздала, авто-пропуск выключен | уведомление, ждём решения оператора |
| Печь опоздала, авто-пропуск включён | пропуск ровно на пороге, `actor = SYSTEM` |
| Занята машина, печь готова | уведомление `helpful=false`, авто-пропуск не срабатывает |
| Уведомление проигнорировано | печь выдаётся штатно, повторно не всплывает |
| Оператор исключил раньше порога | пропуск по решению, причина `OPERATOR` |
| Порог авто-пропуска больше цикла | считается один раз за проход, без накопления |

## 13. Открытые вопросы

1. Лимит исключений за проход — 2 или зависит от числа печей?
2. Кто имеет право исключать: оператор, мастер, оба?
3. Политика возврата по умолчанию: следующий проход или вне очереди?
4. Считается ли исключённая печь в норме выдачи за смену?
5. Нужен ли отдельный отчёт по деградации серий?
6. Порог авто-пропуска: 30 мин (`maxInterval`) или своё значение из технологической карты?
7. Кому адресуется уведомление о передержке: оператору у пульта, мастеру или обоим?
8. Можно ли включать авто-пропуск на реальном производстве или только на стенде?
