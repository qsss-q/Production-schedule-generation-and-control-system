## 2. Исправления

### 2.1. `PostgresApiIntegrationTest` падал на инициализации (`build.gradle.kts`)

Причина не в коде теста и не в БД. Testcontainers 1.20.x (версия из BOM Spring Boot 3.4.4)
обращается к Docker по API 1.32, а Docker Engine 29+ и свежий Docker Desktop принимают
только API ≥ 1.40/1.44. В логе теста:
`client version 1.32 is too old. Minimum supported API version is 1.40` →
`Could not find a valid Docker environment`.

Исправление: `extra["testcontainers.version"] = "1.21.4"` в `build.gradle.kts`. Тест не
менялся, не отключался и не удалялся. Docker при запуске тестов по-прежнему нужен.

### 2.2. После перезапуска backend оставался «действующий» график чужой временной линии

Найдено при проверке вживую. Симулятор живёт в памяти и после перезапуска приложения
(а также после «Сброса», загрузки снимка, смены seed/схемы, импорта печей) начинает
заново с 05.10 08:00. Прогон графика в PostgreSQL при этом оставался `CALCULATED`:
шкала времени показывала операции, к которым симулятор не имеет отношения, позже они
массово уходили бы в `OVERDUE` с уведомлениями, а ручная правка ставила бы в симулятор
план из старой линии. Это стало заметно после перехода на `ddl-auto: update`
(раньше схема пересоздавалась при каждом старте).

Исправление (без изменения симулятора и архитектуры):

- `SimulatorService` — счётчик поколения `generation()`, растёт при каждой замене
  экземпляра симулятора;
- `ScheduleRunService.syncTick()` — если поколение отличается от того, для которого
  посчитан прогон, прогон переводится в `ARCHIVED` (данные остаются в БД, ничего не
  удаляется), в журнал пишется `SCHEDULE_RUN_ARCHIVED`; график формируется заново кнопкой;
- тест `ScheduleRunServiceTest.simulatorReset_archivesStaleRun_insteadOfTrackingOtherTimeline`.

Проверено вживую: после `docker restart coke_factory_app` и после «Сброса» активного
прогона нет, в журнале запись об архивации, новый график формируется и отслеживается.

### 2.3. Публичный туннель запускался по умолчанию (`docker-compose.yml`)

Сервис `tunnel` (cloudflared) поднимался при каждом `docker compose up` и публиковал
в интернет интерфейс и API без авторизации (в том числе удаление и сброс). Сервис
не удалён, он переведён в профиль:

```bash
docker compose --profile tunnel up --build -d
docker compose logs tunnel        # ссылка https://...trycloudflare.com
```

Обычный `docker compose up --build` поднимает только БД, backend и frontend и не зависит
от доступа к Cloudflare.

### 2.4. Документация с испорченными именами файлов (`docs/`)

В `docs/` лежали две копии документов 00–11 и документы 12–14 с именами в неверной
кодировке (`╨┐╤А╨╡...md`). Ссылки из `README.md` на `docs/13-…` и `docs/14-…` из-за этого
не открывались. Файлы с испорченными именами — более новые версии (они описывают текущий
код), поэтому они переименованы в правильные имена и заменили старые копии. Прежние версии
документов 00–11 остаются в истории git (`git show HEAD:docs/...`).

Также обновлены: `docs/12` (эндпоинты экспорта температуры), `docs/14` (версия

## 4. Спорные моменты ТЗ

### 4.1. Приоритеты операций — оставлены

ТЗ прямо требует «настройку параметров расписания: … приоритетов». В проекте приоритет
(1 — обычный, 2 — высокий, 3 — срочный) задаётся по умолчанию в настройках, меняется для
операции (`PATCH /api/operations/{id}/priority`, ручная правка) и **уменьшает допустимый
порог опоздания** (порог / приоритет), то есть срочная операция раньше становится
`OVERDUE` и раньше даёт уведомление. Порядок выдач приоритет не меняет, поэтому
технологическое ограничение H1 (серийность 9-2) не нарушается. Противоречия требованиям
нет, удалять нечего. Устаревшее поле `urgentPriority` в настройках сохранено для
совместимости и в логике не используется.

### 4.2. Окно смены и шаг между выдачами — риск для демо, код не менялся

Окно смены реализовано как жёсткое ограничение: операция, не помещающаяся до конца смены,
переносится на начало следующей. Коксовая батарея работает круглосуточно, поэтому при
стартовых настройках из `data.sql` (смена 08:00–20:00, шаг 15 мин при расчётном
Δt = 840/69 ≈ 12,17 мин) график растягивается и печи передерживаются. Замер на старте
симуляции (B2, `POST /api/v1/schedule-runs`):

| Шаг, мин | Окно смены | Макс. передержка, мин | Ожидание печей, мин | Длина плана, мин |
|---|---|---|---|---|
| 15 | 08:00–20:00 (по умолчанию) | 870,8 | 22 673 | 1 660 |
| 15 | 00:00–23:59 | 208,2 | 7 138 | 1 035 |
| 12 | 08:00–20:00 | 749,1 | 8 133 | 1 543 |
| 12 | 00:00–23:59 | **2,8** | **24,5** | 837 |

Это не ошибка кода, а следствие требований к ограничениям и стартовых значений, поэтому
логика не менялась. Для демонстрации перед формированием графика выставить в левой панели
шаг 12 и окно смены 00:00–23:59, а ограничение сменой показывать отдельно как пример
временного ограничения. Если команда решит поменять стартовые значения в `data.sql`, они
применятся только к пустой БД (существующий том не перезаписывается).

## 7. Известные ограничения (не критичные, не исправлялись)

- Политика удержания (`HOLD_WARNING`, `holdNotifyMin`, `holdAutoSkipMin`) хранится, логики нет.
- Валидаторы H1–H9: автоматически проверяются только H1 и H4.
- Нет аутентификации и ролей; PostgreSQL проброшен на хост `:5432`.
- `spring.jpa.show-sql: true` — в логе backend много SQL (синхронизация раз в секунду).
- Старый `PUT /api/operations/{id}` меняет операцию без причины; правильный путь с причиной

- Демонстрационные операции и уведомления из `data.sql` не привязаны к прогону.
