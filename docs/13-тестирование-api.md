# Тестирование API и проверка Docker-развёртывания

## Назначение

Набор проверяет HTTP-контракт backend API отдельно от внутренней реализации симулятора. Симулятор не переписывается и не тестируется повторно в рамках API-набора: его собственные тесты остаются в `simulator/src/test`.

## Автоматические тесты backend

Запуск из корня проекта:

```powershell
.\gradlew.bat test
```

Основной новый класс: `src/test/java/org/example/coke_factory/api/ApiControllerContractTest.java`.

Это controller-slice тесты на Spring MockMvc в standalone-режиме. Контроллеры настоящие, а репозитории и сервисы заменены Mockito-моками. Поэтому они проверяют маршрутизацию, HTTP-методы, параметры, сериализацию, коды ответа, единый формат ошибок и факт делегирования в сервис/репозиторий, но не являются проверкой PostgreSQL или бизнес-логики планировщика.

### Покрываемые группы API

| Группа | Проверки |
|---|---|
| `/api/equipment` | список, фильтр по типу, отсутствие записи, доступность |
| `/api/ovens` | список и отсутствие записи |
| `/api/operations` | фильтр, печь, статус, диапазон дат, ближайшие операции, приоритет |
| `/api/settings` | список, отсутствие активного профиля, проверка шага |
| `/api/notifications` | список, непрочитанные, отметка прочитанным, удаление отсутствующей записи |
| `/api/audit` | общий журнал и фильтр по сущности |
| `/api/temperature` | выборки по ID и номеру печи |
| `/api/v1/schedule-runs` | список, активный прогон, получение прогона и операций, создание, сравнение, CSV-экспорт |
| `/api/v1/schedule-operations` | ручное изменение операции |
| `/api/v1/import` | делегирование CSV-импорта печей и машин |
| `/api/v1/ovens`, `/api/v1/machines` | управление доступностью и проверка неизвестного кода машины |
| Ошибки | некорректный JSON и неверные значения параметров/настроек |

## Единый формат ошибок

`ApiExceptionHandler` теперь применяется ко всем REST-контроллерам:

- `IllegalArgumentException` → HTTP 400, код `VALIDATION_FAILED`;
- нечитаемое тело запроса → HTTP 400, код `UNREADABLE_BODY`;
- необработанная ошибка → HTTP 500, код `INTERNAL_ERROR`.

Ответ имеет общий конверт `success: false` и объект `error`. Обычные ответы legacy API `/api/...` сохраняют прежнюю структуру; новый конверт используется для ошибок.

## Smoke-тест Docker API

После запуска контейнеров:

```powershell
docker compose up --build -d
.\scripts\smoke-api.ps1
```

Скрипт выполняет безопасные GET-запросы к OpenAPI и основным группам API. Он проверяет, что frontend-independent backend доступен на `http://localhost:8080` и основные read endpoints отвечают 2xx.

Если backend опубликован на другом адресе/порту:

```powershell
.\scripts\smoke-api.ps1 -BaseUrl "http://localhost:8081"
```

## Что не доказывает именно MockMvc-контрактный набор

1. Реальная интеграция JPA-репозиториев с PostgreSQL и корректность схемы — это отдельно проверяет `PostgresApiIntegrationTest` на описанных сценариях, но не исчерпывающе для всех сущностей.
2. Сквозные сценарии с настоящим Docker Compose и браузером.
3. Алгоритмическая корректность B1/B2/B3 и точность симуляции — это отдельная зона симулятора.
4. Полноценная авторизация и разграничение прав — в текущем приложении они не реализованы.

Реальное взаимодействие API и PostgreSQL дополнительно проверяется интеграционными тестами Testcontainers, описанными ниже. Мок-тесты не выдаются за проверку базы данных.


## Интеграционные тесты PostgreSQL

В `src/test/java/org/example/coke_factory/api/PostgresApiIntegrationTest.java` добавлены тесты на настоящем PostgreSQL 15 через Testcontainers. Контейнер создаётся автоматически на время тестового класса; H2 и моки базы не используются. Проверяются:

- доступность PostgreSQL, создание схемы и загрузка демонстрационных данных;
- создание, чтение, обновление и удаление оборудования через REST API с проверкой фактических строк SQL;
- сохранение связи `coke_ovens.equipment_id` с записью справочника оборудования.

Для запуска необходимы Docker Desktop / Docker Engine и доступ к образу `postgres:15-alpine` (при первом запуске образ скачивается). Тестовая база изолирована от рабочей: используется отдельный временный контейнер и `create-drop`; рабочий Docker volume проекта не затрагивается. После тестов контейнер удаляется.

Команда запуска: `./gradlew test` (Windows PowerShell: `.\gradlew.bat test`). Если Docker не запущен, интеграционные тесты не смогут стартовать.

Эти тесты не проверяют алгоритмы симулятора и не меняют его код. Они также не заменяют полный end-to-end прогон всей системы в Docker.
